# End-to-end harness review, 2026-08-25

A review of the end-to-end suite's design, configuration and state: what was wrong with
it, what running it then found, and what changed.

The review was commissioned as a look at the harness. It turned into more than that,
because the baseline run was red before anything was touched: **18 of 264 browser tests
had been failing since 2026-08-23** and nothing had noticed.

Then fixing one configuration line found three more things. The local gate had been
building a *development* bundle rather than the artifact that ships (E2E-H-008). Making
it build the real one turned three passing tests red, and each of the three was a
genuine defect the development bundle had been hiding: a navigation that dropped a
signed-in person onto the marketing site, a colour token used against a background it
was never measured for, and a test asserting a button no shipped build can render.

Thirty-two findings follow, most severe first. Each names the file and line that proves
it. Where a defect is reasoned rather than observed, it says so, because
`docs/observatory/develop/quality-gates.md` sets the standard at **seen to fail** and
"reasoned to fail" is a different claim.

Identifiers are stable and do not run in order: the document is arranged by severity,
the numbers by the order things were found. Cite them as `E2E-H-001`.

## Why this was worth doing

`docs/testing/LOCAL.md` opens with the reason: GitHub Actions on this account can be
billing-blocked, so local runs are the gate. A gate is worth what its weakest guarantee
is worth, and six of the findings below are ways this one could report success without
having tested what it claimed. One of them, E2E-H-002, is why the 18 red tests went
unnoticed for two days.

Two of the findings are about the measurements themselves. A ratchet that publishes the
wrong number (E2E-H-016) or counts the wrong thing (E2E-H-027) is not a weak gate, it is
a misleading one, and both were believed for as long as they were prose. They are gates
now, with self-tests.

## What was already good

Recorded because a review that lists only faults misrepresents the thing.

- 46 spec files, 270 `test(` blocks, 911 `expect(` lines, and **zero** instances of
  `.only`, `test.skip`, `test.fixme` or `test.todo`. Nothing is quarantined.
- The four-states discipline is real: 92 `page.route` stubs exist so loading, empty and
  error states are provable, not just the happy path.
- 34 of 46 specs run an axe scan, and `e2e/tests/helpers/a11y.ts` finishes every running
  animation before scanning, because a fading element is a different colour on every
  frame. Someone found that the hard way and wrote it down.
- `helpers/api.ts` carries the data-space header on every fixture write, with a docblock
  explaining that a helper omitting it "would silently write to the real graph while the
  browser is on demo".
- `workers: 1` is deliberate, correctly reasoned, and stays.

## Method

The review ran in one order, and it matters, because a fix applied before a baseline
cannot be shown to have fixed anything.

1. **Read before running.** The configuration, the six helpers, all 46 specs by
   summary, the workflow, the local runner, and the two documents that claim to
   describe them. Findings were taken from reading three sources against each other
   rather than from any one of them: E2E-H-007 is only visible with
   `helpers/api.ts`, `apps/web/src/lib/api.ts` and the config open together, and
   E2E-H-013 is only visible with the spec and Playwright's own type declarations
   open together.
2. **Baseline, unmodified.** `./scripts/ci-local.sh --full` against the tree at
   `d411ee4`, before a single edit, so that any later red is attributable.
3. **Change, then re-run the same command.** Same script, same isolated ports, same
   disposable database.
4. **Re-measure the ratchets** and diff the spec files for removed assertions.

Every defect above carries the file and line that proves it. Where a defect is latent
rather than currently firing, it says so and names what makes it fire, because
"reasoned to fail" and "seen to fail" are different claims and this repository
distinguishes them.

## What the runs did not touch

The `vitae` development database was not seeded, truncated or read. `scripts/ci-local.sh`
keeps its own `vitae_e2e` database and binds API 4010, web 5183 and buildsvc 8797, which
is why this mattered: `pnpm seed` truncates before it writes, and the documented local
recipe in `LOCAL.md` points it at whatever `DATABASE_URL` names.

Checked at the end rather than assumed:

```
vitae:     1452 nodes     (the development graph, untouched)
vitae_e2e:  235 nodes     (seeded and reseeded by every run)
```

Nothing was pointed at the deployment. Application source was touched in exactly three
files, all named in **What changed**, and each one is a defect a test was seen to fail
on first.

## Severity 1: what running it found

### E2E-H-021 - the local gate hangs in its own cleanup and keeps its ports

The most consequential finding, and it only appears when you actually run the thing.
After the baseline run printed its summary, `./scripts/ci-local.sh --full` did not exit.
It sat in its `EXIT` trap for **54 minutes**, holding ports 4010, 5183 and 8797 and the
Auth emulator on 9099. Because `e2e_local()` refuses to start when those ports are in
use, the gate could not be run a second time on the same machine.

**The mechanism.** `e2e_local()` starts the API as:

```bash
VITAE_CI_DATABASE_URL="$E2E_DATABASE_URL" ci_env setsid env ... pnpm --filter @vitae/api start &
SERVICE_PIDS+=("$!")
```

`ci_env` is a shell *function*, so bash forks a subshell to run the job in the
background, and `$!` is that subshell's pid. `setsid`, running inside it, then puts the
real service in a brand new session. The two are unrelated: the recorded pid sits in the
script's own process group, and the service sits in a group of its own.

`cleanup()` then ran `kill -- "-$pid"` against the recorded pid, which named a process
group with **no members**, and `2>/dev/null || true` swallowed the failure. The service
survived. The `wait "$pid"` on the next line then blocked for ever, because that
subshell was itself still waiting on the child nobody had killed.

- **Source:** `scripts/ci-local.sh` `cleanup()` and `e2e_local()`.
- **Measured:** recorded pid 3981531 had pgid 3957883; `ps -eo pid,pgid | awk '$2==3981531'`
  returned **0 rows**. The service ran as pid 3981533 in group and session 3981533.
  The script, pid 3957886, had been alive 54 minutes with its summary already printed.
- **Consequence:** the only gate that runs on this machine leaks an API process, a web
  preview, a build-service container and the Auth emulator on every run, then blocks.
  The second run refuses to start with `E2E port 4010 is already in use`.
- **Seen to fail, and seen to stop failing:** killing process group 3981533 by hand made
  the hung script exit immediately with `EXIT=1`. Nothing else was touched. That is the
  whole proof of the mechanism.
- **Reproduce:** `./scripts/ci-local.sh --full`, then after the summary prints,
  `ps -o pid,etime,cmd -p "$(pgrep -f 'ci-local.sh' | head -1)"` and
  `ss -ltn | grep -E ':(4010|5183|8797)'`.

**Fixed.** `cleanup()` now reaps by port as well as by pid, and its wait is bounded.
Reaping by port is safe here for exactly the reason the script already relies on:
`e2e_local()` refuses to start if any of those ports is in use, so whatever holds one at
cleanup time was started by this run. The emulator gets the same treatment. The comment
in the script records the mechanism so nobody reintroduces it.

Verified by repetition: the three full runs after the fix each exited on their own and
released 4010, 5183, 8797 and 9099, and the run after each started without the port
refusal. Before the fix, the second run could not start at all.

### E2E-H-022 - eighteen browser tests had been failing since 2026-08-23

The baseline was red before a single line was changed: **18 failed, 246 passed** in
14.5 minutes. Every other step in the run passed.

- **Source:** commit `b1413d1` *"feat(marketing): rebuild the public career-move
  experience"*, 2026-08-23.
- **Measured:** that commit rewrote `Landing.tsx` (782 lines changed) and `Manifesto.tsx`
  (237), and updated their colocated unit tests `Landing.test.ts`, `Manifesto.test.ts`,
  `Pricing.test.ts` and `MarketingContent.test.ts` in the same commit. It updated **no

  on 2026-08-10.
- **Consequence:** the colocated tests moved with the code and the browser tests did not,
  so a whole surface lost its end-to-end coverage silently. Nothing caught it, because
  the workflow is billing-blocked and `ci-local.sh --full` is the only thing that runs
  the suite locally.

The 18 divide into three causes:

| Cause | Tests | What moved |
| --- | --- | --- |
| The marketing rebuild | 13: landing 4, manifesto 3, tour 3, sweep 1, visual baselines 2 | headline, list and footer copy; image alt text; the tour going from five stops to seven; two screenshots |
| The private root moved from `/` to `/today` | 3: `shell.spec.ts:21`, `shell.spec.ts:164`, `signin.spec.ts:99` | `App.tsx` mounts `<Route path="/" element={<Navigate to="/today" replace />} />`, and the rail link points at the destination |
| The in-session demo toggle | 2: `shell.spec.ts:221`, `negative.spec.ts:39` | see E2E-H-024 |

**Repaired.** Each spec now asserts the interface that shipped. No assertion was deleted
or weakened: `landing.spec.ts` still carries 15 `expect(` lines, the same count it had
before. Where a claim genuinely no longer holds, the assertion was retargeted at the
thing that now carries it and the test title was corrected to match, rather than dropped.
Two examples: the tour's last stop no longer offers sign-in, so the test now proves
sign-in stays reachable from the primary nav; and the landing page's brand link has the
accessible name `Vitae home`, not `Vitae`.

### E2E-H-024 - the demo toggle dropped a signed-in person onto the marketing site

Three tests exercise the in-session space toggle. All three failed, and the cause is one
line of application code.

`Shell.tsx`'s `toggleSpace()` ends with `navigate('/')`. In this application `/` is not
the app's home: `App.tsx:167` mounts the public marketing `Landing` there, and
`AuthGate` is mounted only at `path="*"` (`App.tsx:288`), which ranks below an exact
path. So `/` never reaches the authenticated tree, and
`<Route path="/" element={<Navigate to="/today" replace />} />` at `App.tsx:338`, which
records what the author meant, is unreachable code.

Switching to the demo space therefore navigated out of the application, unmounting the
shell and with it the banner that says which space you are in.

- **Source:** `apps/web/src/app/Shell.tsx:138-144` against `apps/web/src/App.tsx:167`,
  `:288` and `:338`.
- **Measured:** the trace records the frame URL sequence `/signin` → `/today` → `/`, and
  the string `demo-banner` appears in **0** snapshots while `mk-hero`, the marketing
  hero, appears in one. The failure screenshot is the public landing page.
- **Consequence:** a person clicking "View demo" is thrown out to the marketing site. The
  data space does switch, so returning to any app route shows demo data with no banner
  explaining why, which is the exact confusion the banner exists to prevent.
- **Reproduce:** sign in, click "View demo", observe the marketing page.

**Why the suite did not catch it.** `demo-mode.spec.ts` passed in the baseline, in 3.0s.
Marketing pages are lazy behind `<Suspense fallback={null}>` (`App.tsx:98-105`), so
during the transition React holds the previous frame rather than painting a fallback. The
shell had already re-rendered with `space === 'demo'`, so the banner was on screen for as
long as the marketing chunk took to arrive, and the assertion caught it. The local gate
was building a **development** bundle (E2E-H-008); a production bundle resolves that
chunk fast enough that the banner is never painted at all.

So the test was passing on a race, and passing for a reason unrelated to what it claimed
to prove. Making the gate build the artifact that ships is what turned it red.

**Fixed** in both halves. `Shell.tsx` navigates to `/today`, which is the destination the
unreachable route already named; seen to fail first, on three specs, and seen to pass
after. And the unreachable route is gone, replaced by a comment saying why there is no
`/` in that tree and what it cost while there was one. Dead code that records the opposite
of what the router does is not neutral: it is what told `shell.spec.ts` to assert
`href="/"`, and what made `toggleSpace` look correct.

### E2E-H-025 - a dark-ground colour token used on a near-white button

Found by the same change as E2E-H-024, and worth its own entry because the mistake is a
general one: a colour token carries the contrast it was measured at, and that measurement
belongs to a background.

- **Source:** `apps/web/src/routes/SignIn.tsx:85-90`, the `DEV` badge on the developer
  sign-in button, styled `text-muted`. That resolves to `--ae-muted`, declared at
  `packages/ui/src/styles/tokens.css:36` with the comment
  `/* 7.6:1 / 6.2:1, labels, inactive nav, metadata */`.
- **Measured:** axe `color-contrast`, impact **serious**, tags `wcag2aa`, `wcag143`.
  `fgColor #a3a3a0` on `bgColor #fafaf8`, **2.41:1** against a required 4.5:1. The 7.6:1
  in the token's own comment is against the application's dark ground; this button's fill
  is near-white, so the token was carrying a promise that did not apply.
- **Consequence:** the badge is `aria-hidden`, so assistive tech never announces it, but
  it is plainly visible and a sighted person with low vision cannot read it. It is a
  developer-only affordance, which lowers the blast radius but not the finding: the suite
  asserts **zero** violations, not zero important ones.
- **Why it was invisible:** the same reason as E2E-H-024. The local gate built its bundle
  without the five `VITE_FIREBASE_*` values, so the sign-in screen rendered
  *"No sign-in method is configured"* instead of the developer button, and the badge that
  fails contrast was never on the page to be scanned.

**Fixed.** The badge inherits the button's own foreground rather than naming a token
measured against a different background. The border that distinguishes it is unchanged.

### E2E-H-026 - a test that asserted a control the shipped bundle cannot render

The third finding surfaced by building the artifact that ships, and the clearest of them.

`signin.spec.ts` asserted a four-stop tab order beginning at a "Continue with Google"
button. That button cannot exist in a production build.

- **Source:** `apps/web/src/lib/firebase.ts:32-43`.
  `googleSignInAvailable = apiKey && authDomain && projectId && (useEmulator || !usesDemoConfig)`.
  The local configuration is the demo one, so `usesDemoConfig` is true and availability
  reduces to `useEmulator`, which is
  `isLocalDeveloperRuntime && VITE_FIREBASE_USE_EMULATOR === 'true'`, and
  `isLocalDeveloperRuntime` requires `import.meta.env.DEV`. The docblock above it states
  the rule outright: *"no environment variable can switch this on in a shipped SPA"*.
- **Measured:** the first tab stop is `"Developer sign-inDEV"`, not
  `"Continue with Google"`. The assertion has no counterpart to match.
- **Consequence:** the test passed locally, on a development bundle, and asserted
  something that is false of every artifact the project deploys or that CI builds. It was
  a guarantee about an environment nobody ships.
- **Reproduce:** build the web app with `NODE_ENV=production` and open `/signin`.

**Repaired, and made stronger.** The test now asserts that Google sign-in is **absent**,
which is the actual design rule and a claim worth holding, then walks the three tab stops
that exist and checks the focus ring on the first. Assertion count unchanged at 23 for
the file.

### E2E-H-027 - the accessibility number counted files, and there were no gaps

The suite's own ratchet published "12 specs with no accessibility scan" and the rule "may
only shrink". Both the number and the rule were about the wrong thing.

- **Source:** the ratchet table in the coverage plan, and
  `grep -L expectNoA11yViolations e2e/tests/*.spec.ts`.
- **Measured:** twelve specs call no scan. Every route those twelve navigate to is scanned
  by another spec, the one that owns that screen:

  | Reached by a spec with no scan | Scanned by |
  | --- | --- |
  | `/resume/tailor` | `tailor.spec.ts`, before and after picking a target |
  | `/people` | `person.spec.ts`, `directories.spec.ts` |
  | `/search` | `search.spec.ts` |
  | `/graph`, `/import`, `/import/duplicates` | `graph.spec.ts`, `import.spec.ts`, `duplicates.spec.ts` |
  | `/intros`, `/ask/people`, `/trash`, `/resume/outputs` | `intros`, `ask`, `trash`, `outputs` |
  | `/`, `/signin` | `landing.spec.ts`, `signin.spec.ts`, `foundation.spec.ts` |
  | `/browse/idea` | `collections.spec.ts`, which scans `/browse/:type` |

  **Screens reached and scanned by nothing: zero.**
- **Consequence:** the metric would have been "improved" by adding eleven duplicate scans,
  costing about thirty seconds a run and covering nothing new. A number that rewards work
  with no effect is worse than no number, because someone will do the work.

**Fixed by replacing the measurement.** `check-e2e-ratchets.mjs` checks the invariant that
matters: every route a spec navigates to must be scanned by some spec. It normalises
legacy addresses through `route_normalisation` (`/welcome` is `/`), so a redirect does not
read as a gap, and `a11y_exempt_routes` takes anything genuinely exempt with a reason.
It reports **0 unscanned** across 39 screens.

One scan was added, and only one, because it was the only state nothing covered: the
demo-space shell in `demo-mode.spec.ts`. The banner is chrome that exists in no other
state.

### E2E-H-028 - every signed-in test re-proved the sign-in screen

- **Source:** `e2e/tests/helpers/auth.ts`.
- **Measured:** `signIn` loaded `/signin`, waited up to ten seconds for the developer
  button to render, clicked it, waited for the redirect, then waited for Today. Roughly
  240 of the 264 tests begin with it, and the suite is serial by design, so the cost is
  paid 240 times in sequence on every run.
- **Consequence:** wall clock, and a coupling nobody wanted. Every signed-in spec in the
  suite depended on the sign-in screen rendering correctly, so a defect there failed
  everything at once and told you nothing about where it was. E2E-H-026 is exactly that:
  a change to the sign-in screen's contents, surfacing as a failure in an unrelated spec.
- **Reproduce:** `grep -c 'signIn' e2e/tests/*.spec.ts`.

**Fixed.** `signIn` mints the session straight from `/auth/dev-login`, which sets the same
httpOnly cookie in the same browser context, seeds the two localStorage keys through
`addInitScript` so they are present before the shell mounts, and goes directly to
`/today`. Driving the sign-in screen is `signin.spec.ts`'s subject and it still does,
which is where that coverage belongs.

The readiness signal is unchanged: Today's register rule, the one element that only
renders once the dashboard query has resolved. The helper cannot pass against a
half-loaded page, which was the property worth keeping.

### E2E-H-029 - the accessibility helper scanned before the stylesheet applied

A latent flake in the helper 35 specs depend on, found by running the suite once more
rather than by reading it.

- **Source:** `e2e/tests/helpers/a11y.ts`.
- **Measured:** `docs.spec.ts:316` failed with axe `color-contrast`, impact serious, ink
  `#333333` on ground `#0f0f0f` at **1.51:1**, with `.docs-root`, `.docs-contents__title`,
  `.docs-contents__name` and `.docs-contents__summary` among the targets. Those are the
  unstyled defaults, not the corpus's palette. The retry passed, and the same test passed
  in four earlier full runs.
- **Consequence:** an intermittent failure that reports a contrast defect the page does
  not have, on whichever route happens to load its CSS in a separate chunk. It costs a
  retry when CI grants one and a red gate when it does not, and it teaches whoever sees it
  that the accessibility scan is unreliable, which is the expensive part.
- **Why it was there:** the helper already solves exactly this problem for animation. Its
  comment explains that a fading element is a different colour on every frame and records
  the false readings that came of scanning mid-flight, "a 27px heading at 2.19:1, a
  primary button at 4.33:1". A stylesheet that has not applied is the same failure with a
  different cause, and nothing waited for it.

**Fixed**, after three attempts, because the helper was early in three separate ways and
each one only became visible once the one in front of it was gone.

| What it did not wait for | What axe then read |
| --- | --- |
| the route's stylesheet, which arrives in its own chunk | `#333333` on `#0f0f0f`, **1.51:1** - unstyled defaults |
| animations that *start* after the one finishing pass | `#6e6e6c` on `#0f0f0f`, **3.75:1** - a token mid-fade |
| a row mounting on the frame after the first quiet one | `#313130` on `#0f0f0f`, **1.47:1** - the same fade, earlier |

Every one of those foregrounds is `--ae-muted`, a token declared at 7.6:1 against that
exact ground. None of them is a fact about the design. They are facts about the moment the
scan happened, and a scan that cannot tell those apart teaches whoever reads it that the
accessibility gate is unreliable, which is the expensive part.

So the helper now waits for every pending `link[rel="stylesheet"]` and for
`document.fonts.ready`, then finishes animations repeatedly until **two consecutive
frames** find nothing left to finish, bounded at twenty passes so an infinite animation
cannot hold the scan open. A stylesheet that errors settles rather than blocks:
one that will never arrive is a different defect, and waiting on it would report that
defect as a timeout somewhere unrelated.

Two specs were also at fault rather than the helper, and both are the same mistake.
`docs.spec.ts` scanned immediately after `goto` while its two siblings in the same file
wait for a heading and a table. `cloud/access.spec.ts` waited for the banner, which paints
above the queue and therefore arrives before it. Both now wait for the thing they are
about to scan.

### E2E-H-030 - nothing checked the workflow, and the workflow has not run

The pipeline is billing-blocked, so `.github/workflows/ci.yml` has not executed in a long
time. Nothing else read it either. A file that no runner runs and no gate checks is a
file that drifts, and every fault in it is discovered by whoever eventually turns the
billing back on.

- **Source:** `.github/workflows/ci.yml`, 54 steps across 6 jobs, and the absence of any
  script that reads it. `scripts/ci-local.sh` runs the same *commands*, which
  `check-ci-mirror.mjs` (E2E-H-003) now proves, but neither one parses the workflow.
- **Consequence:** the class of fault a pipeline reports in its first ten seconds is
  invisible here. A mis-indented block, an action reference whose tag moved, a `run:` step
  with an unbalanced quote, a `pnpm test:proze` typo. None of those reach a command, so
  running every command locally says nothing about them.
- **Reproduce:** before the fix, introduce any of the above and run every local gate. All
  of them pass.

**Fixed as far as it can be.** `scripts/check-workflow.mjs`, run by `pnpm test:workflow`
in `test:all`, in `ci-local.sh` and in the workflow itself, checks the six things that can
be checked without a runner:

| Check | The fault it catches |
| --- | --- |
| the file parses as YAML | the whole job never starts |
| every `uses:` is pinned to a commit sha | a moving tag, which the repository claims (FR-016) and enforced nowhere. 18 are pinned |
| every `run:` block is valid shell | an unbalanced quote, a stray `fi` |
| every `pnpm <script>` exists in `package.json` | a typo that fails the job rather than the step |
| every `needs:` names a real job | a rename that silently orphans a dependency |
| every job declares `runs-on` and `timeout-minutes` | a hung command sitting for the account maximum |

`${{ }}` expressions are substituted before the shell check, and pnpm's own verbs are
known, because a gate that reports `pnpm audit` as a missing script gets switched off
within a day and then the real faults go unread too. Both cases are in the self-test.

**What this is not.** It is not evidence the workflow passes. Nothing local is. The
honest position is now three separate claims rather than one vague one: the workflow is
structurally valid (`test:workflow`), everything it runs is also run locally
(`test:mirror`), and everything run locally passes (`ci-local.sh --full`). The gap that
remains is the runner itself, and it is not a local decision.

### E2E-H-031 - nothing in the browser handled the 402 a locked workspace returns

The defect the coverage plan recorded in section 2.3 and left for later.

- **Source:** `apps/api/src/middleware/workspace.ts` `entitlementGate` refuses every non-GET
  from a `read_only` or `deletion_pending` workspace with **402 PAYMENT_REQUIRED**, and 70
  endpoints are marked blocked-when-read-only. `apps/web/src/lib/api.ts:62-79` has no
  status branching of any kind.
- **Measured:** `grep -rn '402\|PAYMENT_REQUIRED' apps/web/src packages` returned **zero
  hits**. A 402 became `ApiError(402, 'PAYMENT_REQUIRED', ...)`, handled identically to a
  500. The two download helpers were worse, discarding the server's message outright:
  `throw new ApiError(res.status, 'DOWNLOAD', 'download failed')`.
- **Consequence:** on a locked workspace every write control across all 60 private routes
  stayed enabled and clickable. The only feedback was whatever toast the failing mutation
  happened to raise through the global `MutationCache`, and any mutation with its own
  `onError` swallowed even that. Nothing named the state, and nothing pointed at the two
  things that still worked.
- **The part that makes it worse:** `useAuth().workspace` has carried `accessState` the
  whole time (`apps/web/src/lib/auth.tsx:48-56`). `App.tsx` read it for routing. No screen
  read it at all. The information was already in the browser and simply never shown.

**Fixed.** The shell renders a `role="status"` banner when the workspace is `read_only` or
`deletion_pending`, in the one piece of always-mounted chrome above the routed content,
beside the demo banner whose pattern it borrows. The two states are named separately
because they mean different things, and both doors the API leaves open are on it: the
export that still works and the billing screen that can undo it. Wording follows
`Billing.tsx`'s own chips so the banner and that screen tell one story.

Three cases in `Shell.test.tsx`, two of them seen to fail first. The third asserts the
banner stays **absent** on an active workspace, which is what stops it becoming chrome
everyone learns to ignore.

**What it does not do** is disable the controls themselves. That is 60 routes and a
different change. The banner is the part that was missing.

### E2E-H-032 - Cloud mode had no browser coverage at all

- **Source:** `grep -rn 'billing\|cloud' e2e/tests/` returned nothing.
- **Measured:** the API side is well covered. `cloud.integration.test.ts` has four cases
  over bootstrap, tenant isolation, the 402, provider events and webhook signatures.
  `Billing.test.tsx` has six, with `api`, `useAuth` and `lib/paddle.js` all mocked. Between
  them they never load a page.
- **Consequence:** every claim about what a person *sees* in Cloud mode was untested,
  including the one in E2E-H-031. `docs/testing/source-test-map.json` says so about the
  checkout loader in as many words: *"Billing.test.tsx substitutes a mock for this module,
  so the checkout script loader and its readiness probe are unproven. Needs a
  browser-level test."*
- **Why it stayed that way:** turning the flag on breaks about a quarter of the default
  suite by design. `apps/api/src/db/space.ts` stops reading `x-vitae-space`, so ten
  `signInDemo` specs read the real graph while the banner still says demo. That is a silent
  wrong answer, which is worse than a failure, and it is why the coverage plan says to
  design Cloud coverage rather than retrofit it.

**Fixed.** A second suite at `e2e/cloud/`, with its own `playwright.cloud.config.ts` and
its own phase in `scripts/ci-local.sh`, run as a separate Playwright invocation after the
default one.

Three things made it much cheaper than the plan feared:

1. **The browser bundle needs no rebuild.** `cloudEnabled` reaches the SPA from
   `GET /auth/me` at run time, not from a `VITE_` flag baked at build time. Only the API
   restarts. The five `VITE_PUBLIC_*` values gate marketing copy and SEO only.
2. **Dev sign-in still works.** `authGate`'s Cloud branch admits `via: 'dev'`, and the dev
   identity's email is `OWNER_EMAIL`, so it claims `workspace-legacy-real` on bootstrap
   and inherits everything `pnpm seed` wrote.
3. **The access state can be moved honestly.** The API suite writes
   `workspace_lifecycles.access_state` directly because it holds a database handle. A
   browser test does not, and a backdoor would prove the banner renders for a value
   someone typed rather than a state the system can reach. The helper posts a **signed
   provider event** to the real webhook instead, through the real signature check and the
   real `applyPaddleWebhook` path.

One hazard found while building it, and worth keeping: `applyPaddleWebhook` orders by
`provider_updated_at` and silently drops anything not newer than what it holds. A helper
that reuses a clock delivers an event, gets a `200`, and changes nothing. So each delivery
carries a strictly increasing stamp, the helper waits for the control plane to report the
state it asked for, and `ci-local.sh` resets the control plane before the suite so a
previous run's stamps cannot order ahead of this one's.

## Severity 1: the ways the gate could report a false pass

### E2E-H-001 - nothing refuses a focused test

`test.only` narrows a run to the tests it marks and reports success for the rest.
Playwright ships `forbidOnly` for exactly this, and the config never set it.

- **Source:** `e2e/playwright.config.ts`, the whole file; no `forbidOnly` key.
- **Measured:** `grep -c forbidOnly e2e/playwright.config.ts` returned 0. The suite
  itself is clean: `grep -rn '\.only(' e2e/tests | wc -l` returned 0.
- **Consequence:** one committed `test.only` reduces a 264-test gate to one test, and
  the gate still says it passed. Nothing in the pipeline notices.
- **Reproduce:** add `.only` to any test, run `pnpm e2e`, observe the run go green
  having executed one case.

**Fixed.** `forbidOnly: !process.env.VITAE_E2E_FOCUS` in the config, and
`playwright/no-focused-test` as a lint error, so it is caught at review time as well
as run time. The environment variable keeps deliberate local debugging possible.

### E2E-H-002 - the only gate that runs discards its own evidence

`scripts/ci-local.sh` is the gate on this machine. It ran Playwright without `CI` in
the environment, and every diagnostic in the config was conditioned on `CI`.

- **Source:** `scripts/ci-local.sh:298-306` (the Playwright invocation) against
  `e2e/playwright.config.ts:37-50`. `CI=1` appears once in the script, at line 149,
  inside `api_integration()` only.
- **Measured:** with `CI` unset the run resolves to `retries: 0`, `reporter: [['list']]`,
  `trace: 'on-first-retry'` and `video: 'off'`. A retry-only trace with zero retries can
  never be written.
- **Consequence:** a failure in the local gate leaves a stack trace in terminal
  scrollback and nothing else. No trace to open, no video, no HTML report, no JUnit.
  The config's own comment defends local `retries: 0` as leaving "a signal worth
  looking at"; there was nothing to look at.
- **Reproduce:** before the fix, `./scripts/ci-local.sh --full` with any failing spec,
  then `ls e2e/playwright-report` and find no such directory.

**Fixed.** Artifacts are now unconditional in the config: `trace: 'retain-on-failure'`,
`video: 'retain-on-failure'`, `screenshot: 'only-on-failure'`, and the `html` and
`junit` reporters always. `ci-local.sh` sets `CI=1` for the run, so it also gets the
same single retry CI gets, and prints the artifact paths when the run fails.

### E2E-H-003 - the local mirror was not a mirror

The script's header says *"Local equivalent of .github/workflows/ci.yml"* and *"This
mirrors the CI jobs in the same order"*. It ran 8 of the workflow's gates and skipped 9.

- **Reproduce:** `diff <(grep -o 'pnpm [a-z:]*' scripts/ci-local.sh | sort -u) <(grep -o 'pnpm [a-z:]*' .github/workflows/ci.yml | sort -u)`.

### E2E-H-004 - the local e2e run never compiled the documentation corpus

### E2E-H-006 - two workspaces that ran in no job at all

## Severity 2: the suite disagreed with itself about the time

### E2E-H-007 - three clocks, none of them pinned

The fixtures, the browser and the specs' own date arithmetic each read a different
timezone, and the configuration pinned none of them.

| Who | What it used | Source |
| --- | --- | --- |
| Fixture API calls | `x-vitae-tz: UTC`, hardcoded | `e2e/tests/helpers/api.ts:27` |
| The browser | `Intl.DateTimeFormat().resolvedOptions().timeZone` | `apps/web/src/lib/api.ts:59` |
| The specs themselves | the Node process's zone | `today.spec.ts:82`, `trash.spec.ts:74,84,94,108`, `helpers/fixtures.ts:48` |

- **Measured:** `grep -c 'timezoneId\|TZ' e2e/playwright.config.ts` returned 0, and
  `grep -n 'TZ:' .github/workflows/ci.yml` returned nothing. The development machine
  reports `EEST+0300`; GitHub and CodeBuild runners are UTC.
- **Consequence:** a record the fixture stamps for "today" in UTC is yesterday's row
  on a screen three hours ahead. `today.spec.ts:82` computes a weekday name in the
  runner's zone and compares it against one the browser rendered in its own. The two
  agree for twenty-one hours a day and disagree for three, so the failure reproduces
  only between 00:00 and 03:00 local and never in CI at all. This is latent, not
  currently firing: it was found by reading the three sources together, and the
  mechanism is stated rather than claimed as observed.
- **Reproduce:** `TZ=Pacific/Kiritimati pnpm e2e -- tests/today.spec.ts` on a stack
  seeded near a day boundary.

**Fixed.** One knob sets all three. `e2e/playwright.config.ts` assigns
`process.env.TZ` at module scope, before any spec reads the clock, and passes the same
value as `timezoneId` to the browser context. `locale: 'en-US'` is pinned with it,
because the specs and the product copy both assume that formatting. `VITAE_E2E_TZ`
moves all three together.

### E2E-H-008 - the local gate measured a development bundle

- **Source:** `scripts/ci-local.sh` `production_build` step and the web build inside
  `e2e_local()`; the mechanism is documented at length in
  `scripts/check-web-budgets.mjs:12-29`.
- **Measured:** the repository `.env` carries `NODE_ENV=development`. Vite captures
  `isNodeEnvSet = !!process.env.NODE_ENV` before it loads the config file, so a value
  in `.env` outranks `vite build`'s own `production` and nothing inside
  `vite.config.ts` can intervene.
- **Consequence:** two of them. The local `pnpm build` emitted the development JSX
  runtime and ran roughly a megabyte larger than what ships, and
  `VITAE_REQUIRE_BUDGETS=true pnpm test:performance` refuses to judge it, so the budget
  gate could not run locally at all. Separately, the browser the e2e suite drove was
  not the browser bundle CI serves.
- **Reproduce:** `pnpm build && VITAE_REQUIRE_BUDGETS=true pnpm test:performance`, and
  read `web budgets: this is a development build, so its size means nothing.`

**Fixed.** `NODE_ENV=production` is exported for the build commands only, which is
what makes `isNodeEnvSet` true and the build real. It is scoped deliberately:
`packages/config` refuses to boot an API with `NODE_ENV=production` and
`AUTH_ENABLE_DEV_LOGIN=true`, which is every API start in the script.

**This is the finding that found the others.** Building the real artifact turned three
passing tests red, and all three were right to go red: E2E-H-024, E2E-H-025 and
E2E-H-026. A development bundle differs from a shipped one in ways that matter to a
browser test. It resolves lazy chunks at a different speed, which is what hid a
navigation defect behind a race; and `import.meta.env.DEV` is true in it, which changes
what the sign-in screen offers at all. Every test that ran against it was, to that
extent, testing something the project does not deploy.

### E2E-H-009 - two specs asked for more time than their test was allowed

- **Source:** `e2e/tests/resume-full.spec.ts:45,54` and

## Severity 5: enforcement that lived in prose

### E2E-H-015 - the ratchets were grep commands nothing ran

- **Source:** the coverage plan defines seven ratchets: spec count,
  `expect(` count, zero focused or skipped tests, `waitForTimeout` count, `toBeTruthy`
  count, a11y coverage, and the skip count in the generated artifact.
- **Measured:** all seven are shell commands in a Markdown table. No script, no gate
  and no lint rule runs any of them.
- **Consequence:** the rules held because the people following them were careful, not
  because anything checked.

**Fixed.** In two halves, because they are two different kinds of rule.

The shape rules are lint errors: `no-focused-test`, `no-skipped-test`, `no-page-pause`,
`no-element-handle`, `prefer-web-first-assertions`, `prefer-to-have-count`,
`prefer-to-have-length`, `valid-expect`, `expect-expect`, `no-conditional-in-test`,
`no-conditional-expect` and `no-wait-for-timeout`. All of them, at error. The single
surviving sleep carries an `eslint-disable-next-line` with the reason written beside it,
which is the difference between an exception and a hole.

The count rules are a gate: `scripts/check-e2e-ratchets.mjs`, holding the numbers in
`docs/testing/e2e-ratchets.json`, run by `pnpm test:ratchets` in `test:all`, in
`ci-local.sh` and in the workflow. It has a self-test of thirteen cases, because a
ratchet nobody has seen fail is a ratchet nobody should trust.

### E2E-H-016 - the sleep ratchet undercounts by two

- **Source:** the ratchet greps for `waitForTimeout`.
- **Measured:** `grep -rn 'waitForTimeout' e2e/tests | wc -l` returns 1, at
  `ask.spec.ts:37`. `grep -rn 'setTimeout(' e2e/tests/*.spec.ts` returns two more, at
  `repositories.spec.ts:65` and `import.spec.ts:93`, each sleeping 5 s.
- **Consequence:** the published figure is 1 where there are 3, so a new raw sleep can
  be added without moving the number anyone watches.
- **Not a defect in the tests themselves.** All three sleeps are honest. The 500 ms one
  proves a request was *not* sent, which no retrying assertion can express, and the two
  5 s ones sit inside `page.route` handlers to delay a stubbed response and hold the
  screen in its loading state, which is the correct way to test that state. What is
  wrong is the measurement, not the code.

**Fixed.** `check-e2e-ratchets.mjs` counts `waitForTimeout(` and `setTimeout(` as the
same thing, because they are, and the self-test proves each spelling is caught on its own.
The coverage plan now publishes 3 and points at the gate rather than at a
grep, and its table records which of its own numbers were wrong and why.

### E2E-H-017 - the Playwright config was excluded from lint

- **Source:** `eslint.config.js:37`, the global ignore `'**/*.config.ts'`.
- **Consequence:** the file holding the clock, the timeouts, the retry policy and the
  focused-test guard was the one file in the e2e workspace the linter never read. No
  type-aware rules reach `e2e/` either, so a floating promise in a spec, which in this
  suite means an assertion that never runs, is invisible.

**Fixed.** `'!e2e/playwright.config.ts'` un-ignores it, and it is inside the new
Playwright lint scope.

## Severity 7: cost without a correctness consequence

### E2E-H-020 - a sign-in round trip on every fixture call

- **Source:** `e2e/tests/helpers/api.ts:20-31`.
- **Measured:** `apiHeaders()` runs a `page.evaluate` to read the data space and posts
  `/auth/dev-login` to mint a fresh token, and it is called by every one of `apiGet`,
  `apiPost`, `apiPatch` and `apiDelete`. A fixture that creates a person, an
  organisation and an edge pays three evaluates and three sign-ins.
- **Consequence:** wall-clock only. Correctness is unaffected, and the comment above it
  explains why the bearer is needed at all: Playwright will not share the page's
  httpOnly cookie with a sibling API origin.
**Fixed.** The token is cached against the page in a `WeakMap`, so it is minted once per
test and dies with the page. A failed mint is evicted rather than cached, so the next call
retries instead of replaying the rejection. The data-space header is deliberately **not**
cached: `demo-mode.spec.ts` and `negative.spec.ts` both toggle the space mid-test, and a
stale header would write to the graph they just left.

### What was deliberately not done

One thing, and it is not a local decision.

- **The workflow itself has still not run**, and nothing here can make it. What was one

  everything it runs is also run locally (`test:mirror`), and everything run locally
  passes (`ci-local.sh --full`). The runner is a billing decision.

Two smaller judgements, stated rather than buried:

- **A locked workspace's write controls are still enabled.** The banner names the state
  and offers both doors; disabling every control across 60 private routes is a different
  change with its own design.
- **`/` still shows a signed-in visitor the marketing page.** Removing the unreachable
  redirect (E2E-H-024) made that visible instead of contradicted. Whether the root should
  recognise a session is a product question, and the place to answer it is the public

## Process report

**What was done, in order.** The configuration, the six helpers, the specs, the workflow
and the local runner were read first, against each other rather than one at a time. Three
of the findings exist only in the gaps between files: E2E-H-007 needs `helpers/api.ts`,
`apps/web/src/lib/api.ts` and the Playwright config open together; E2E-H-013 needs the
spec and Playwright's own `.d.ts`; E2E-H-002 needs the shell script and the config.

Then the baseline ran, unmodified, at `d411ee4`. It was red, which changed the shape of
the work: what had looked like a configuration review became a configuration review plus
a repair of coverage that had been silently lost for two days.

Then the fixes, then the same command again.

**Six things were only findable by running it.** This is the part worth keeping.

1. The gate hung in its own cleanup and held its ports (E2E-H-021). Reading `cleanup()`
   does not tell you that `$!` is the wrong pid; watching the script sit for 54 minutes
   after printing its summary does.
2. The 18 red tests (E2E-H-022). The specs and the components both looked reasonable in
   isolation. Only the browser knew the headline had changed.
3. The a11y defect on the landing page (E2E-H-023) sat behind a test that could not reach
   its own scan, so it stayed invisible until the assertion above it was repaired.
4, 5 and 6. E2E-H-024, E2E-H-025 and E2E-H-026 all followed from one line in
   `ci-local.sh`: building the bundle that ships instead of a development one. Each was a
   test that had been passing for a reason unrelated to what it claimed. That is worse
   than a failing test, because a failing test tells you something.

**One mistake, kept here because the record is the point.** The first regenerated
screenshot baseline was invalid. It was produced from a bundle built without the five
`VITE_FIREBASE_*` values, so the sign-in splash rendered its error state, *"No sign-in
method is configured"*, and that error state very nearly became the committed reference
for what sign-in should look like. It was caught by opening the PNG, which is what the
spec's own docblock has always told the reader to do. The baselines were regenerated
inside the gate's stack instead, which sets those five values because
`.github/workflows/ci.yml` does.

**The suite caught me making a mistake, which is the point of it.** Rewriting `signIn` to
seed localStorage through `addInitScript` looked right and was not: an init script runs
before *every* navigation, not once, so it re-imposed the starting data space on each
`goto` and silently undid an in-session toggle. `demo-mode.spec.ts` switched to demo,
navigated to the tailor rail, and arrived back in the real graph with nothing to find.

It is worth recording for two reasons. The helper is used by roughly 240 tests, and the
one spec that changes space mid-test is what failed, which is the suite doing exactly the
job it exists for. And the failure was legible in about a minute, because the trace and
the failure screenshot were both on disk (E2E-H-002). Before this work the same mistake
would have produced one line of scrollback.

The fix is to seed rather than enforce: write the key only when it is absent.

**The Cloud suite caught its own helper, twice, which is the argument for the helper.**

`deliverSubscriptionStatus` does not trust the `200` it gets back. A stale provider event
is accepted and discarded, and a duplicate looks identical from outside, so the helper
waits for the control plane to report the state the event asked for. That assertion
failed on the first real run, with the message it was written to print: *"the canceled
event was accepted but the workspace did not reach read_only"*.

The cause was mine. Each delivery carried a stamp a minute further into the future than
the last, from a module-level counter. Playwright restarts its worker after a failing
test, the counter reset to zero, and the fresh worker's first stamp landed behind a
stored one several minutes ahead. Every event after that was accepted and dropped.

The fix is to stop stamping into the future at all: take the real clock, nudged forward
only enough to break a tie inside one millisecond. Nothing then writes a timestamp that
has not happened, so the sequence increases across worker restarts and across runs
without any coordination. Had the helper simply asserted the `200`, this would have
surfaced as three unrelated billing failures and a long afternoon.

**One assertion of mine was just wrong**, and worth saying so plainly.
`billing.spec.ts` asserted the screen says "Checkout is not configured".
It does, on one of three forks, and by the time that test runs the earlier specs have left
a subscription behind, so a different fork renders. The claim I actually wanted does not
depend on the fork: no path through that screen may offer a way to pay in a build with no
provider token. That is what it asserts now.

**A note on the two measurements that were wrong.** These are the findings worth carrying
forward, because the mistake in each is easy to repeat.

The sleep count (E2E-H-016) was wrong because the rule was written as the *command* that
measured it rather than the property it wanted. `grep waitForTimeout` is not "no fixed
waits", it is "no fixed waits spelled this way", and the second spelling arrived without
anybody deciding to allow it.

The accessibility count (E2E-H-027) was wrong because it counted the artefact that was
easy to count. Twelve specs call no scan; zero screens go unscanned. Improving the
published number would have meant adding eleven duplicate scans, paying thirty seconds a
run for nothing. A metric that rewards useless work is worse than none, because the work
gets done.

Both are now gates that state the property and are self-tested against it.

**What was not resolved.** One thing, and it is not a local decision: the workflow has
still never run. Everything else the earlier drafts of this document listed as open is
closed, including the two that looked largest. Cloud mode has a browser suite
(E2E-H-032), and the 402 defect the coverage plan recorded in 2023 words and left for
later has a fix with a test that was seen to fail first (E2E-H-031).

Two judgements are recorded rather than taken, because they are product decisions:
a locked workspace's write controls are still enabled, and `/` still shows a signed-in
visitor the marketing page.

**One last note on method.** Three of the last four findings came from the same move:
taking a thing the repository already said and checking whether it was true. The campaign
brief said the sleep count was 1; it was 3. It said twelve specs lacked an accessibility
scan; no screen lacked one. `ci-local.sh` said it mirrored the workflow; it ran eight of
seventeen gates. None of those were lies. They were measurements that stopped being
re-taken, which is what happens to every number that lives in prose. All of them are gates
now, and all three gates have self-tests, because the only thing worse than an unchecked
claim is a checked one that cannot fail.
